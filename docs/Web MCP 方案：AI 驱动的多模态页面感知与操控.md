# Web MCP 方案：AI 驱动的多模态页面感知与操控

- [ ] 一、背景与动机

### 1.1 竞品分析结论

通过对航旅纵横 AI 助手的分析，其实现本质上是 **伪 AI 操控**：

- 底层仍是传统的 **intent→action** 路由架构，AI 仅作为意图分类的包装层
- 虽然暴露了 Native MCP，但仅封装了跳转/点击等基础操作
- **没有页面感知能力** — AI 不知道自己在操作什么内容，无法理解页面元素
- 场景覆盖单一（仅酒店），Tools 能力单薄，大量常见意图无法处理

### 1.2 核心问题

AI 想要真正理解页面并保证性能，**不能仅靠纯视觉截图识别**，必须在应用层开发对应的 **Native MCP** 或 **Web MCP** 供 AI 调用。

> **核心思路：让 AI 直接获取结构化页面数据，而非仅依赖视觉猜测。**

---

## 二、Web MCP 的本质

传统 MCP 是给 AI 提供外部工具调用能力（查天气、查数据库）。

**Web MCP 则是把页面本身变成一个可交互的工具集合** — AI 不再"看截图猜"，而是直接调接口拿数据、读结构、发操作。

可以理解为：**每个 H5 页面都自带一份「自我描述文档」，AI 通过 MCP 协议读取并操作它。**

---

## 三、核心能力分层

### L1 — 页面结构读取（Read）

| 能力 | 说明 |
| --- | --- |
| DOM 树读取 | 获取当前页面的精简 DOM 树，过滤装饰性节点 |
| 语义化提取 | 提取标题、列表项、按钮、表单字段及其关联数据 |
| 结构化输出 | 返回结构化 JSON，而非原始 HTML |

### L2 — 页面状态感知（State）

| 能力 | 说明 |
| --- | --- |
| 场景标识 | 当前页面路由/场景识别（酒店列表页、详情页、订单页...） |
| 可视区域 | 滚动位置、当前可见范围内的元素 |
| UI 状态 | 加载中/空状态/错误态等状态标识 |

### L3 — 数据层暴露（Data）

| 能力 | 说明 |
| --- | --- |
| API 数据直出 | 页面背后的 API 响应数据（酒店原始数据：价格、评分、位置标签、距离等） |
| 筛选/排序状态 | 当前生效的筛选条件、排序规则 |
| 用户上下文 | 登录态、用户偏好、历史行为（按需过滤隐私数据） |

### L4 — 操作执行（Action）

| 能力 | 说明 |
| --- | --- |
| 精确交互 | 点击某元素、输入文本、选择筛选项、滚动到指定位置 |
| 组件级操作 | 「筛选距地铁站 500m 内」「按评分排序」「对比第 2 和第 4 个酒店」 |
| 页面导航 | 前进、后退、跳转指定路由 |

## 四、架构方案对比

### 方案 A：页面级 MCP（专属模式）

每个页面开发独立 MCP server，暴露该页面专属 tools。

| 维度 | 说明 |
| --- | --- |
| 优点 | 精准、性能好、类型安全、可针对页面定制 |
| 缺点 | 开发成本高，每上新页面都要开发对应 MCP |
| 适用 | 核心高频页面（酒店、机票、火车票） |

### 方案 B：通用 DOM MCP + 语义标注层

底层一个通用 DOM 读取/操作 MCP，上层按页面注入语义标注（给关键组件打 `data-ai-*` 标签）。

| 维度 | 说明 |
| --- | --- |
| 优点 | 复用性强，新页面接入成本低，统一维护 |
| 缺点 | 需要前端配合打标签，初期推动有阻力 |
| 适用 | 长尾页面、快速迭代的页面 |

### 方案 C：混合模式（推荐）

核心页面做专属 MCP，长尾页面用通用 DOM MCP。

| 维度 | 说明 |
| --- | --- |
| 优点 | ROI 最优，核心体验有保障，长尾可快速覆盖 |
| 缺点 | 需要维护两套体系，架构设计复杂度较高 |
| 适用 | 整体落地策略 |

## 五、关键设计问题

### 5.1 性能优化

| 策略 | 说明 |
| --- | --- |
| **批量读取** | 一次调用返回页面结构 + 数据 + 状态，避免多次 RPC 往返 |
| **主动推送** | 页面状态变化时主动通知 AI，减少轮询 |
| **按需加载** | 仅暴露当前场景需要的 MCP tools，减少上下文 token 消耗 |
| **缓存机制** | 页面结构未变化时复用上次结果，仅 diff 增量数据 |

### 5.2 安全边界

| 维度 | 策略 |
| --- | --- |
| **数据可见性** | 用户隐私数据（支付信息、完整手机号等）需过滤或脱敏 |
| **操作权限分级** | 查询/筛选类操作可直接执行；涉及支付、下单的操作需二次确认 |
| **操作审计** | 所有 AI 执行的操作需记录日志，支持回溯与追溯 |

### 5.3 与多模态的配合

Web MCP 不是替代多模态视觉，而是与之配合：

- **Web MCP 为主** — 结构化数据读取、精确操作执行（高性能、高准确）
- **多模态为辅** — 处理 MCP 无法覆盖的场景（如截图校验、非标准页面、第三方 H5）
- **兜底机制** — 当 MCP 不可用时，降级为纯视觉方案

## 六、与航旅纵横方案对比

| 维度 | 航旅纵横 | 本方案（Web MCP） |
| --- | --- | --- |
| 页面理解 | ❌ 无页面感知，纯序号跳转 | ✅ 结构化读取页面元素及语义 |
| Tools 丰富度 | ❌ 仅跳转/点击 | ✅ Read + State + Data + Action 四层能力 |
| 意图覆盖 | ❌ 仅酒店场景 | ✅ 多场景，可扩展 |
| 数据来源 | ❌ 不读页面，硬编码意图 | ✅ 直接获取 API 数据，AI 基于数据决策 |
| 性能 | 低（依赖大模型逐轮理解） | 高（批量读取 + 按需推送） |
| 本质 | 套 AI 壳的传统路由 | 真正的 AI 原生页面感知与操控 |

### 8.2 Web MCP SDK 注入方式

| 方式 | 说明 | 适用场景 |
| --- | --- | --- |
| **全局脚本注入** | 在 Webview 初始化时注入 MCP SDK，所有 H5 页面自动可用 | 统一容器，可控性强 |
| **CDN 脚本引入** | 各业务页面自行引入 `<script src="mcp-sdk.js">` | 已有页面改造，渐进式接入 |
| **NPM 包依赖** | 以 `@trip/mcp-sdk` 形式作为业务依赖引入 | 新项目开发，类型安全 |

### 8.3 通信协议

Web MCP SDK 与 AI Orchestrator 之间通过 **JSON-RPC 2.0** 协议通信：

**工具调用示例（AI → 页面）：**

```json
{
  "jsonrpc": "2.0",
  "id": "req-001",
  "method": "tools/call",
  "params": {
    "name": "get_hotel_list",
    "arguments": { "page": 1, "sort": "price_asc" }
  }
}
```

**工具返回示例（页面 → AI）：**

```json
{
  "jsonrpc": "2.0",
  "id": "req-001",
  "result": {
    "content": [
      {
        "type": "text",
        "text": "{\"hotels\":[{\"id\":\"h001\",\"name\":\"上海外滩W酒店\",\"price\":1280,\"rating\":4.8,\"tags\":[\"外滩\",\"地铁站200m\"]}]}"
      }
    ]
  }
}
```

## 九、MCP Tools 接口规范（以酒店场景为例）

### 9.1 工具分类

| 分类 | 工具名 | 说明 | 输入 | 输出 |
| --- | --- | --- | --- | --- |
| **读取类** | `get_page_info` | 获取当前页面基本信息 | - | 页面类型、标题、路由 |
| **读取类** | `get_hotel_list` | 获取酒店列表数据 | page, sort, filters | 酒店数组（结构化） |
| **读取类** | `get_hotel_detail` | 获取单个酒店详情 | hotelId | 酒店详情 JSON |
| **读取类** | `get_filter_options` | 获取可选筛选项 | filterType | 选项列表 |
| **状态类** | `get_page_state` | 获取页面当前状态 | - | 滚动位置、加载状态、可视区域 |
| **操作类** | `click_element` | 点击页面元素 | elementId 或 selector | 操作结果 |
| **操作类** | `apply_filters` | 应用筛选条件 | filters | 筛选后结果 |
| **操作类** | `scroll_to` | 滚动到指定位置/元素 | target | 滚动结果 |
| **操作类** | `navigate` | 页面导航 | route, params | 导航结果 |

### 9.3 元素标识方案

每个可交互元素必须有唯一标识，供 AI 精准操作：

| 标识方式 | 示例 | 说明 |
| --- | --- | --- |
| `data-ai-id` | `data-ai-id="hotel-card-1"` | 推荐方案，语义明确 |
| `data-ai-role` | `data-ai-role="price-sort-btn"` | 标注元素角色/功能 |
| `element_id` 自动生成 | `el_h001_price` | SDK 根据 DOM 结构自动生成 |

## 十、典型交互流程

### 场景：「帮我看看外滩附近 500 块以内评分最高的酒店」

```
1. 用户语音输入 → ASR 转文字
2. AI 理解意图：查询外滩区域、预算≤500、按评分排序
3. AI 调用 get_page_info → 确认当前在酒店列表页
4. AI 调用 get_filter_options → 获取可用的筛选维度
5. AI 调用 apply_filters → 
   { "district": "外滩", "max_price": 500, "sort": "rating_desc" }
6. 页面返回筛选结果（结构化 JSON）
7. AI 读取结果，用自然语言回复用户：
   "外滩区域 500 元以内评分最高的酒店是 XX，评分 4.7，
    距南京东路地铁站 300 米，今晚还有房，要看看详情吗？"
8. 用户说"看看" → AI 调用 get_hotel_detail → 展示详情
```

**与传统方案的关键差异：**

- 第 5 步：AI 不是盲目跳转，而是**基于结构化数据做决策**
- 第 6 步：AI **读到了完整的酒店数据**（价格、评分、位置、标签），而非只知道"第一个"
- 整个流程中，AI 始终知道自己在操作什么，每一步都有数据支撑

## 十一、错误处理与异常恢复

| 异常场景 | 处理策略 |
| --- | --- |
| **MCP SDK 未加载/不可用** | 降级为纯视觉方案（截图 + 多模态理解） |
| **页面结构变更导致元素找不到** | 返回详细错误信息（元素不存在/选择器失效），AI 可重试或切换策略 |
| **网络超时/请求失败** | 重试机制（最多 2 次），超时后通知 AI 当前页面加载失败 |
| **AI 调用了不存在的 Tool** | 返回可用工具列表，引导 AI 使用正确的工具 |
| **页面跳转到未知场景** | 自动调用 get_page_info 重新识别当前页面，同步上下文 |
