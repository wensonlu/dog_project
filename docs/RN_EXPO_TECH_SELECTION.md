# React Native CLI vs Expo 调研与选型（Dog Project）

## 1. 背景与目标

当前项目移动端基线为 `React + Vite + Capacitor`。团队计划在不影响现有交付的前提下，尝试将单个页面使用 React Native 重构，以验证：

- 交互体验是否提升
- 性能与稳定性是否满足预期
- 团队维护成本是否可控

本次调研聚焦两条 RN 技术路线：

- React Native CLI
- Expo

## 2. 对比维度

评估维度包括：

- 上手和交付速度
- 原生能力可控性
- 第三方原生 SDK 接入难度
- 开发与调试体验
- 构建发布复杂度
- 团队技能匹配度
- 与现有 Capacitor 架构并存的可行性

## 3. React Native CLI

### 3.1 优势

- 原生工程完全可控（Xcode/Gradle、构建参数、启动流程）。
- 对复杂或冷门原生 SDK 接入更直接。
- 深度性能优化、底层问题排查空间更大。

### 3.2 劣势

- 工程初始化和环境维护成本高于 Expo。
- iOS/Android 双端构建细节较多，对原生经验要求更高。
- 首次可用版本的产出速度通常慢于 Expo。

### 3.3 适用场景

- 产品长期目标是 RN 作为主客户端，并需要强原生可控性。
- 业务需要重度原生能力（如复杂音视频、硬件、定制推送链路等）。
- 团队已有稳定的 iOS/Android 工程能力投入。

## 4. Expo

### 4.1 优势

- 启动快、脚手架完善，适合快速 POC 与渐进试点。
- 开发调试体验友好，前端同学上手成本低。
- 常见移动能力可通过生态模块快速接入。
- 构建与发布链路成熟，便于小团队稳定迭代。

### 4.2 劣势

- 极度定制原生流程时会受到框架边界约束。
- 部分冷门/私有原生 SDK 可能需要额外适配。
- 原生构建细粒度控制不如 CLI。

### 4.3 适用场景

- 先迁移一个或少量页面做体验与成本验证。
- 团队以 Web/React 人力为主，追求更快迭代。
- 现阶段目标是降低试错成本，而非一次性重构全端。

## 5. 结合 Dog Project 的结论

### 5.1 选型结论

当前阶段优先选择 **Expo**。

### 5.2 结论依据

- 现有主链路已在 Capacitor 上稳定运行，不适合大规模重构。
- 当前需求是“单页 RN 重构验证”，Expo 更适合低风险落地。
- 团队可以先在 Expo 完成页面级验证，再决定是否扩大迁移范围。

## 6. 推荐迁移策略（渐进式）

### 6.1 第一阶段（试点）

- 选取高价值、低耦合页面（建议：`/pet/:id` 详情页）。
- 使用 Expo 实现对应 RN 页面，覆盖核心能力：
  - 参数传递（宠物 id）
  - 数据请求（详情、评论等）
  - 登录态与收藏动作

### 6.2 第二阶段（并存）

- 保留 Web 页面作为回退路径。
- 通过 Deep Link 或统一路由协议接入 RN 页面。
- 使用开关控制灰度范围（内部用户或小流量）。

### 6.3 第三阶段（决策）

按以下指标评估是否继续迁移：

- 页面加载与交互流畅度
- 崩溃率与错误率
- 开发/测试/发布人力成本
- 用户反馈与转化变化

若后续出现大量深度原生诉求，再评估迁移到 React Native CLI 的必要性。

## 7. 风险与边界

- 双栈并存（Web + RN）会增加短期维护复杂度。
- 路由、登录态、埋点方案需提前统一协议。
- 如需接入非常规原生 SDK，Expo 方案需预留验证时间。
